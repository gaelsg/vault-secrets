# 2026-08-30 — Onboarding de k8s-mcp-server, primera vez usando vault-admin

Parte de la Idea 6 (ver [`k8s-mcp-server`](https://github.com/gaelsg/k8s-mcp-server) para el detalle completo). Esta entrada es sobre el lado de Vault.

## Cambio
- Política nueva `policies/k8s-mcp-server.hcl` — solo lectura de `secret/data/k8s-mcp-server` y su metadata, mismo patrón que `proxmox-mcp-server`/`observability`.
- Script nuevo `scripts/onboard-k8s-mcp-server.sh` — hace login con el AppRole `vault-admin` (creado en la Idea 2 para exactamente esto), escribe la política, crea el AppRole del proyecto, sube el secreto (`kubeconfig=@archivo.yaml`), y escribe `VAULT_ROLE_ID`/`VAULT_SECRET_ID` en el `.env` del proyecto destino — sin pedir `vault login` con el root token en ningún momento.

## Primera vez que `vault-admin` se usa para lo que se pensó
En la Idea 2, `vault-admin` se creó explícitamente para tareas administrativas rutinarias sin volver a tocar root/unseal — pero hasta ahora (Ideas 2 y 3) cada onboarding nuevo se había hecho con comandos de Vault sueltos, a mano, tras un `vault login` normal. Esta es la primera vez que existe un script reusable que loguea con `vault-admin` por su cuenta, hace el trabajo, y revoca su propio token al final (`vault token revoke -self`) — cierra el círculo de lo que se planeó hace dos ideas.

## Lo que se subió a Vault
Un único secreto (`kubeconfig`) con el YAML completo de un kubeconfig **de solo lectura**: apunta a una `ServiceAccount` (`mcp-agent`, namespace `kube-system`) atada al `ClusterRole` built-in `view` + un `ClusterRole` custom acotado a `get/list/watch` sobre `nodes` — no es el kubeconfig admin que genera k3s por defecto (ese nunca salió del nodo ni pasó por el asistente, ver `k8s-mcp-server/docs/29110/idea6-k8s/04-verificacion.md`).

## Verificado
- `onboard-k8s-mcp-server.sh` corrido de punta a punta: política, AppRole y secreto creados; `.env` de `k8s-mcp-server` recibió las credenciales sin que se imprimieran en la terminal.
- `k8s-mcp-server` arrancando y trayendo datos reales del cluster usando esas credenciales (ver ese repo).
