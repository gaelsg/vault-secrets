# 2026-08-29/30 — Idea #2: Gestión de secretos con HashiCorp Vault

Ver `docs/29110/idea2-vault/` para el detalle formal (plan, requisitos, diseño, verificación con los 7 incidentes reales). Resumen aquí:

## Qué se construyó
- LXC dedicado para Vault (`proxmox-iac/environments/vault`, reusando el módulo de la Idea 1 — cero permisos nuevos en Proxmox necesarios, `tofu@pve` ya cubría el pool `iac`).
- Vault OSS, Raft, TLS con CA propia, KV v2, audit log, AppRole por proyecto.
- `proxmox-mcp-server` migrado: sus tokens de Proxmox/Portainer ya no viven en `.env`, viven en `secret/proxmox-mcp-server`; el servidor los pide vía AppRole al arrancar.

## La lección más grande no estaba en el plan
Vault, a diferencia de todo lo demás gestionado en este proyecto (Proxmox, Portainer, Nextcloud), tiene un modo de fallo real que ningún token de API tiene: **si revocas el root sin plan y algo sale mal, de verdad te quedas afuera** hasta juntar 3 de las 5 llaves de unseal vía `generate-root`. Eso pasó dos veces en esta implementación (un bug de permisos en mi propia política, y un bug en mi propio script que ocultó un fallo real) — cada vez tocó la ceremonia completa. Es exactamente el tipo de operación que en una empresa real solo se hace con runbook y varias personas presentes, no algo que se improvisa.

## Aprendizaje inesperado: `enable_unauthenticated_access`
Vault 2.x bloquea `sys/generate-root` por defecto (403 incluso sin token) a menos que se agregue `enable_unauthenticated_access = ["generate-root"]` en la config — un endurecimiento que no aparecía en lo que yo (el asistente) tenía memorizado de versiones anteriores. Se encontró vía `WebFetch` a la documentación oficial en vivo, no adivinando. Se pudo aplicar con `SIGHUP` (`systemctl reload vault`), sin bajar el servicio.

## Un descuido propio, documentado sin suavizarlo
El primer script de bootstrap (`bootstrap.sh`) tenía un patrón `comando 2>/dev/null && echo ok || echo "(ya existia)"` que interpretaba *cualquier* fallo como "ya estaba configurado" — así se enmascaró un error real de permisos (`mkdir /var/log/vault: permission denied`) y el audit log quedó sin habilitarse en el primer intento, sin que nadie se enterara hasta revisar directamente el log del servicio. Reescrito para comprobar el estado real antes de actuar, no interpretar códigos de salida.

## Decisión de diseño que cambió durante la construcción
El plan original proponía que `proxmox-mcp-server` tuviera fallback a `.env` si Vault no respondía. Al implementar se decidió lo contrario: fail-fast con error claro si Vault está configurado pero no responde, en vez de arrancar con secretos parciales o una copia local potencialmente vieja. Documentado en el diseño como una decisión mejor que la planeada originalmente, no un pendiente.
